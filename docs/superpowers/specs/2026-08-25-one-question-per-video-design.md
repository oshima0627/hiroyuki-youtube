# 1問1本への作り替え

作成: 2026-08-25

## なぜ作り替えるのか

チャンネルにインプレッションが配られていない。実測（2026-08-25、Studio）:

| 動画 | インプレッション | CTR | 視聴 |
|---|---|---|---|
| 08/15 お金の相談7連発 | 17,000 | 1.5% | 292 |
| 08/18 フランス暮らし8連発 | 17 | — | 0 |
| 08/19 仕事の相談10連発 | 6 | — | 0 |

ショートも同じで、最多の1本（視聴17回）ですらショートフィードからの流入は 11.8%（≒2回）。
残りは **YouTube 検索が 76.5%**（検索語: 税理士試験 30.8% / 簿記1級 23.1% / 日商簿記1級 15.4%）。
一方で 8/22 のショートは平均視聴率 100.5%。**見た人は最後まで見ている。配信されていないだけ。**

電話番号の確認が上限に達していてカスタムサムネイルが使えないため、CTR 側のレバーは閉じている。
**いま操作できるのは検索だけ。** タイトルと説明文で狙える。

「◯◯の相談7連発」という総集編は、どの検索語とも一致しない。1問1本にして、
視聴者が実際に打つ語をタイトルに置く。

## 何を作るか

### 全体構成

```
signals.py       SEARCH 語彙を追加（AVOID と同じ形・同じ扱い）
qa.py            split_blocks() が各ブロックに search_words / search_in_title を付ける
                 └ score は変更しない（総集編モードの挙動を据え置く）
plan_single.py   新規。検索語の濃いブロックを1問ずつ選び、1問=1構成案を書く
build_episode.py clips[i].notes（配列）を受け付け、1問に複数枚の解説板を描く
recipe.py        notes 配列を検証する
```

`plan_episode.py`（総集編）は残す。失敗しても戻れる状態を保つ。

### 検索語の測り方

`signals.py` に `SEARCH: dict[str, tuple[str, ...]]` を置く。区分は
資格 / 制度 / 職種・働き方 / 学校 / サービス名。

**`AVOID` と同じく `split_blocks` の中で毎回計算する。`signals.json` に焼き込まない。**
語彙は実測のたびに増えるので、キャッシュしてよい種類のデータではない。

各ブロックに付ける値:

- `search_words` — 一致した語の**集合**。同じ語の連呼で順位を稼げないよう distinct にする
- `search_in_title` — トピックタイトル側で一致したか（真偽値）

**タイトル一致と字幕一致を分けて持つ。** ASR 字幕は固有名詞を崩すので、
字幕だけの一致は誤検出の可能性がある。混ぜると区別できなくなる。

語彙の初期値は**実績のある検索語から始める**。ショートに実際に流入した
「税理士試験」「簿記1級」「日商簿記1級」が起点。以後は Studio の検索語レポートで増やす。
思いつきで並べた語彙表にしない。

### 選別（plan_single.py）

順位: `(search_in_title, len(search_words), score)` の降順。

条件:

- `risk` が空
- `score >= MIN_SCORE`
- 既出区間でない（`plan_episode.used_ranges` を流用）
- 素材尺 120〜180秒

尺の下限を 120 秒に置くのは、完成を 2〜4 分にするため。40秒の素材に解説を足しても
1分台にしかならず、それはショートの領分になる。

### タイトル

`【ひろゆき】{ブロックのタイトル}`。

推測ではない。**実際に検索流入 17回を取ったショート**
「【ひろゆき】簿記1級を取るか税理士を目指すか【切り抜き】」がこの形。

### 解説板を複数枚にする

`build_episode.py` は現状 **1クリップにつき解説板を1枚**しか描かない（`c["note"]` ＋ まとめ1枚）。
1問1本でこのままだと本編の約9割が素材そのままになる。
**「再利用されたコンテンツ」判定にとって、総集編だったときより悪い比率になる。**

`clips[i].notes`（文字列の配列）を受け付け、複数枚を描けるようにする。
既存の `note`（単数）はそのまま動かす。後方互換を壊さない。

`recipe.py` の検証も `notes` に対応させる。1問1本のときは解説の量が
再利用コンテンツ判定に直結するので、**clips が1件のレシピは notes を2枚以上必須**にする。

### ショートとの対応

同じ質問で対にする。ショートはその質問の山場だけを切り、概要欄から長尺へ導線を張る。
自分の長尺から切ったショートは YouTube が想定している使い方で、既存の
`plan_shorts.py` / `used_shorts.json` の仕組みをそのまま使える。

検索で長尺、フィードでショートと、入口を二つ持つ。

## 変えないもの

- `build_episode.py` の描画・連結の本体（`notes` の受け口を足すだけ）
- `upload_youtube.py`、`set_thumbnails.py`
- `plan_episode.py`（総集編モード）
- 15分の上限（電話番号の確認が通っていないため継続。1問1本なら元々当たらない）

## 検証

1. `plan_single.py` を実測データ（`work/` の43本）に対して流し、選ばれた質問と
   一致した検索語を画面に出す
2. 選ばれた1問でレシピを組み、`recipe.validate()` を通す
3. `build_episode.py` で実際に1本ビルドし、完成尺が 2〜4分に入ることを確認する

**「実装しました」では報告にしない。上の3つの実際の出力を添える。**

## 実装中に計測で覆った点（2026-08-25）

設計どおりに作らなかった箇所と、その理由。**推測ではなく実行結果で覆っている。**

### 1問1本は成立しない → 検索語ごとに2〜4問

`work/` の43本・1504ブロックに対して計測した結果:

- 単一トピック（タイトルに " / " を含まない）のブロック: 593件
- そのうち検索語がタイトルに入り、risk 無し、score >= 0.5: **13件**
- そのうち素材尺 120〜180秒: **0件**（実際の尺は 43〜118秒）

1問はそもそも1分前後しかない。2〜4分にするには解説板を10枚近く積むことになり、
「1分の素材＋文字スライド」になる。総集編より悪い。

→ **同じ検索語を共有する2〜4問**を1本にする。1本が1つの検索意図に対応していれば、
タイトルは検索語で書ける。スクリプト名も `plan_single.py` ではなく `plan_keyword.py`。

### 語数で並べると結合ブロックが勝つ

`split_blocks` は近いトピックを結合するので、タイトルが " / " で連なったブロックができる。
それは中身が小さな総集編で、話題が多いぶん検索語も多い。語数順の上位を占めてしまった。

→ **単一トピックのブロックだけを候補にする。**

### 字幕一致で束ねると主題がずれる

字幕（ASR）一致も含めて束ねたとき、「看護師」の回に
**「サグラダ・ファミリア完成と『未完成のロマン』」**が入った。話の中で一度触れただけで主題ではない。

→ **束ねるのはタイトル一致だけ。** `search_title_words` と `search_text_words` を分けて持ち、
字幕側は語彙を育てる手がかりに留める。候補は 34ブロック → 6ブロックに減ったが、中身は正しくなった。

### 解説板の尺は 11.5 秒ではない

`NOTE_SEC = 11.5` は総集編の実測平均。短い解説文だと約6秒だった（実測4枚: 6.8 / 6.3 / 4.9 / 5.8 秒）。
文字数依存なので、`plan_keyword.py` の見込みは「予測」ではなく「最短」として出す。

## 検証結果（2026-08-25 実行）

- `plan_keyword.py`（一覧）: 候補6ブロック / 2問以上を組める検索語 2語（NISA、iDeCo）
- `plan_keyword.py --word NISA`: 2問・本編2:50・完成は最短 3:25
- 解説板の複数枚生成: 4枚を実際にレンダリングし、ファイル名の衝突が無いこと・
  `note_is_current` のキャッシュ判定が効くことを確認
- `recipe.validate()`: 既存の総集編7本がそのまま通ること、
  「2問・板2枚」を弾き「2問・notes計4枚」を通すことを確認
